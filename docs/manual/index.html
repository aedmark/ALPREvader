Foundations

Begin with the product contract, the privacy boundary, and the present maturity of the project.

Privacy-first evasive routing

#
overviewuser-facingrouting

ALPR Evader calculates car routes around known Automatic License Plate Reader cameras on hardware controlled by the user.

What it does

  1. Accepts an origin and destination and returns route geometry, distance, and turn instructions.
  2. Penalizes roads that cross known camera Capture Zones, while still permitting a route through a zone when no alternative exists.
  3. Displays known zones and the calculated route in a browser map.

How it works

A local Docker Compose stack combines PostGIS camera data, GraphHopper road routing, a FastAPI orchestration layer, and a Leaflet page. The API converts nearby zones into a per-request GraphHopper custom model.

Why it works this way

D-001 records self-hosting as the core product choice: a hosted route service would learn the user's coordinates. D-002 and D-003 preserve route availability while strongly preferring camera-free roads.

Location privacy invariant

#
privacysecurityknown-gap

Origins and destinations are intended never to leave the local stack, but the current browser implementation does not yet satisfy that contract.

What it does

  1. Treats a user's origin, destination, travel pattern, and viewed map area as sensitive data.
  2. Requires any new third-party host or location disclosure to be reviewed in the decision and security records.
  3. Currently leaks typed addresses to public Nominatim and reveals viewed areas through third-party map asset requests.

How it works

Route calculation and camera lookup run locally, but index.html loads Leaflet from unpkg, map tiles from OpenStreetMap, and sends address searches to nominatim.openstreetmap.org. The API also logs raw route coordinates at INFO.

Why it works this way

D-004 makes local handling a product invariant because location disclosure defeats the reason to self-host. P2-01 through P2-03 track the code changes needed to make the promise true.

Host prerequisites

#
setupdockerresources

The intended environment is a Linux or macOS host with Docker Compose, a GraphHopper jar, map storage, and enough memory for the selected extract.

What it does

  1. Runs the complete application as local containers.
  2. Uses Java heap settings that default to 24 GB, which is too large for many laptops.
  3. Requires files that are not yet fetched or created by the repository's setup flow.

How it works

Docker Compose builds the Python services, starts PostGIS and a Java 17 GraphHopper container, and bind-mounts the repository into the routing and ingest containers. The routing command expects graphhopper-web-9.1.jar and car.json in the checkout.

Why it works this way

D-001 accepts local resource cost in exchange for keeping routing under the user's control. P1-01 through P1-03 and P4-05 exist because the current defaults and missing files make that trade-off unnecessarily difficult.

State ingest workflow

#
operationingestopenstreetmap

A shell command downloads one US state extract, imports its ALPR nodes, and can switch GraphHopper to that state's roads.

./scripts/ingest_state.sh <state-name>

What it does

  1. Downloads <state>-latest.osm.pbf from Geofabrik.
  2. Extracts OSM nodes tagged man_made=surveillance and surveillance:type=ALPR into PostGIS.
  3. Optionally updates config-alpr.yml, removes the old road graph cache, and restarts GraphHopper.

How it works

scripts/ingest_state.sh downloads the PBF and invokes scripts/ingest_state.py inside the ingester container. The Python handler inserts each matching node and a 50-meter polygon, committing in batches. A state switch rewrites GraphHopper's input filename and rebuilds graph-cache/.

Why it works this way

Per-state extracts limit download size and GraphHopper memory use. D-008 changes the intended database policy from accumulating stale rows to replacing rows from the same source while retaining other states; that behavior is planned but not implemented.

  • Pipeline scripts/ingest_state.sh

operationweb-uirouting

After ingest and graph preparation, the intended entry point is the browser UI at http://localhost:8000.

  2. Serves index.html from the API root and lets the user enter an origin and destination.

Persistent data and rebuild costs

#
operationstoragerecovery

Camera rows, road graphs, and downloaded map extracts outlive individual container runs and have different recovery costs.

What it does

  1. Keeps PostGIS data in the pgdata Docker volume.
  2. Keeps GraphHopper's generated road graph in graph-cache/.
  3. Keeps downloaded .osm.pbf files and the GraphHopper jar outside Git.

How it works

Compose owns the database volume; GraphHopper writes the bind-mounted cache, often as root; ingest scripts write map extracts in the repository root. Switching routing states removes only the graph cache through a disposable container.

Why it works this way

Reusing these artifacts avoids expensive downloads and graph builds. Their different lifecycles are protected because deleting pgdata loses ingested cameras and rebuilding a graph can consume substantial time and RAM.

Routing System

Trace a route from browser input through spatial selection and GraphHopper's custom model.

Capture Zones

#
domainpostgisrouting

A Capture Zone is a polygon around a known camera that receives a severe routing penalty.

What it does

  1. Represents proximity to a camera as an area rather than a point.
  2. Lets GraphHopper penalize any road segment that enters the area.
  3. Currently produces an effective radius of roughly 100 meters because a 50-meter buffer is applied during ingest and again during API queries.

How it works

The ingester transforms each WGS84 camera point to EPSG:3857, buffers it by 50 meters, and stores the result in SRID 4326. Both camera API queries then apply another 50-meter geography buffer before returning GeoJSON.

Why it works this way

An area models uncertain camera coverage better than a zero-width point. D-009 chooses a 75-meter radius applied exactly once; P3-01 tracks the correction from the current doubled buffer.

Evidence
  • Current SQL scripts/ingest_state.py
  • Second buffer main.py

Route request flow

#
data-flowapigraphhopper

Each request selects nearby zones, creates an avoidance model, calls local GraphHopper, and translates the result for the browser.

What it does

  1. Receives origin and destination coordinates in GeoJSON order: [longitude, latitude].
  2. Selects cameras within a padded corridor, not every camera in the database.
  3. Returns plain GeoJSON route geometry, distance in meters, turn instructions, and a camera count.

How it works

  1. FastAPI pads the coordinate bounding box by 0.1 degrees and queries intersecting zones from PostGIS.
  2. It assigns each zone a GraphHopper custom-model area with a multiply_by: 0.01 priority rule.
  3. It posts the payload to local GraphHopper with a 10-second timeout and returns the first path.

Why it works this way

D-002 selects per-request models so camera data can change without rebuilding the road graph. Limiting zones to a corridor controls payload size; the fixed 0.1-degree padding is an implementation heuristic, not a measured guarantee.

  • Architecture flow docs/ARCHITECTURE.md

Evasive route API

#
apicontractfastapi

POST /api/v1/routes/evasive is the browser's route-calculation interface.

POST /api/v1/routes/evasive {origin:[lon,lat], destination:[lon,lat], profile:"car"}

What it does

  1. Validates that origin and destination each contain exactly two numbers.
  2. Returns route_geometry, cameras_evaded, distance_meters, and instructions.
  3. Returns 400 for recognized out-of-bounds GraphHopper errors, 500 for database failures, and 502 for routing-engine request failures.

How it works

Pydantic parses the request and FastAPI serializes RouteResponse. The synchronous handler opens a database connection per request, builds the GraphHopper payload, and maps selected downstream failures to HTTP exceptions.

Why it works this way

The explicit JSON contract keeps the single-page client small and uses GeoJSON coordinate order end to end. Current validation does not check coordinate ranges, and only the car profile is configured despite accepting arbitrary profile text; P4-04 and P3-04 track those gaps.

Camera bounding-box API

#
apigeojsonmap

GET /api/v1/cameras/bbox supplies Capture Zone features for the currently visible map area.

GET /api/v1/cameras/bbox?min_lon=…&min_lat=…&max_lon=…&max_lat=…

What it does

Returns a GeoJSON FeatureCollection containing each intersecting camera's node ID and zone polygon.

How it works

FastAPI coerces four query parameters to floats, PostGIS intersects the requested envelope with stored polygons, and the handler converts database GeoJSON strings into response objects. The page calls it on map readiness and after moveend.

Why it works this way

Viewport-scoped loading avoids sending the entire camera database to the browser. There is currently no coordinate-range validation or maximum bbox size, so P4-04 covers abuse and accidental oversized queries.

Soft-avoidance custom model

#
graphhopperalgorithmtrade-off

GraphHopper receives camera zones as dynamic areas whose traversal priority is multiplied by 0.01.

What it does

  1. Strongly discourages a route from entering known Capture Zones.
  2. Allows unavoidable zone crossings instead of making some destinations unreachable.
  3. Disables contraction hierarchies for the request so the dynamic model can take effect.

How it works

build_custom_graphhopper_payload assigns each selected camera a stable request-local area name, embeds its GeoJSON feature, adds an in_<area> priority rule, sets ch.disable to true, and requests unencoded path points plus instructions.

Why it works this way

D-003 explicitly rejects a hard zero multiplier because a camera may sit on the only physical access route. The cost is slower flexible routing and the possibility that a returned route still passes a camera.

Camera count semantics

#
known-gapapiaccuracy

The response field cameras_evaded currently counts selected corridor cameras, not cameras proven to be avoided.

What it does

Reports the number of Capture Zones included in the GraphHopper custom model for a request.

How it works

The endpoint returns len(zones) immediately after querying the padded bounding box; it does not compare the chosen path with those polygons.

Why it works this way

The current name overstates the evidence. P3-02 plans to intersect the returned route with zones and distinguish cameras avoided from cameras still passed.

Docker Compose topology

#
architecturedockerservices

The runtime is split into PostGIS, GraphHopper, an optional ingester, and the FastAPI service that also serves the UI.

What it does

  1. Runs db for spatial camera state, routing for the road graph, ingester for one-shot OSM imports, and api for HTTP orchestration and the static page.
  2. Publishes the API on port 8000 and GraphHopper on port 8989; PostGIS is kept inside the Compose network.

How it works

The API depends on both database and routing services and reaches them by Compose DNS. The ingester uses a profile so normal startup does not leave an ingest container running. Shared bind mounts give GraphHopper and the ingester access to map files and scripts.

Why it works this way

D-001 uses familiar, replaceable local components rather than a hosted backend. Service separation keeps spatial storage, road routing, and request orchestration independently understandable, at the cost of more setup and memory.

Camera data model

#
databasepostgisschema

PostGIS stores an OSM node identifier, a point location, and a Capture Zone polygon in SRID 4326.

What it does

Supplies spatially searchable camera locations and precomputed coverage polygons to both routing and map-display queries.

How it works

The ingester issues parameterized inserts into alpr_cameras and relies on node_id being unique for ON CONFLICT. Both API queries use ST_Intersects against a WGS84 envelope. The schema itself is currently missing from the repository.

Why it works this way

PostGIS provides the geometry transformations and intersection queries required by the routing flow (D-001). P1-01 will make the implicit schema reproducible, and D-008 requires adding a source-extract field for correct re-ingest behavior.

API trust boundaries

#
securityvalidationcors

All request data is untrusted; current validation and browser access controls are intentionally documented as incomplete.

What it does

  1. Uses parameterized SQL for route and bbox queries.
  2. Applies basic Pydantic shape validation and a 10-second GraphHopper timeout.
  3. Currently allows any origin through CORS, logs route coordinates, and omits range and bbox-size limits.

How it works

FastAPI performs type coercion, psycopg2 binds SQL parameters, and requests.post enforces the downstream timeout. CORS is configured with allow_origins=["*"] and credentials enabled.

Why it works this way

Parameterized queries and timeouts provide minimum boundary protection. P2-03, P2-04, and P4-04 exist because a local service can still leak sensitive data or be driven by malicious websites.

Failure modes and recovery

#
operationsreliabilitytroubleshooting

Most runtime failures are diagnosed through container or API logs and recovered by restoring the unavailable local component.

What it does

  1. Surfaces database failures as HTTP 500 and GraphHopper request failures as HTTP 502.
  2. Recognizes some out-of-bounds routing errors as HTTP 400.
  3. Leaves graph-building progress, heap exhaustion, and missing schema diagnosis to service logs.

How it works

The API catches database and requests exceptions, while Docker records service exits and GraphHopper import output. Operators wait for graph import, start missing services, select an in-bounds state, or adjust heap size depending on the symptom.

Why it works this way

Inferred from the current pre-release scope: direct logs are the only observability layer. The architecture document centralizes recovery guidance so handlers and UI code do not carry operational prose.

Verification strategy

testingevidencequality
